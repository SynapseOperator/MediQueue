# ADR-0002：P1 核心关系模型与数据库约束

- 日期：2026-11-16
- 状态：P1 实施决定；实际验证以阶段记录及对应 commit 的 CI 为准
- 依据：[PRD V1.1](../spec/MediQueue_PRD_V1.1.md)、[数据库设计 V1.1](../spec/MediQueue_Database_Design_V1.1.md)、[模拟支付设计 V1.1](../spec/MediQueue_Mock_WeChat_Payment_Design_V1.1.md)

## 背景与范围

P1 基于已合并的 P0 PR #1 建立数据库模型。旧文档中的“尚未实现”和仅限 P0 描述保留为历史背景；实际实现与验证另见该阶段记录。本文描述数据库决定，不扩大业务范围。

P1 将十张核心业务表逐表落为 migration，并提供合成种子和真实 MySQL 数据库测试。保持单应用、单 MySQL 8.4。认证、Eloquent 业务模型、预约事务服务及模拟支付闭环留在后续阶段，不用基础表的存在冒充功能完成。

## 决定一：按规范保存实体与历史事实

十张核心表保持 V1.1 职责，不添加医院、微信交易尝试或通知事件等额外业务表。既有 `sessions`、`migrations` 为两张技术表，不计核心表数量。

主键及相应外键均为 `BIGINT UNSIGNED`；核心实体时间为非空 `DATETIME(3)`，审计仅有 `created_at`。事件未发生时保留 NULL。UTC 用于保存和比较，医院日期与展示使用 Asia/Shanghai。金额为正数 `DECIMAL(10,2)`，币种 CNY；本阶段不增加免费挂号、部分退款或真实渠道。

所有业务 FK 明确采用 UPDATE/DELETE RESTRICT。该机制保护引用完整性，不等于禁止删除未被引用的末端记录或自动实现角色、权限、历史不可变性。后续服务继续负责主数据停用、预约/支付/退款不物理删除及已承诺时段保护。

`slots.occupied_count` 是需要核对的汇总冗余，`appointments.fee_amount` 是交易时金额快照，`schedules.department_id` 是该次出诊科室事实。保留这些不同语义，不复制完整患者/医生信息，也不笼统声称所有字段均满足严格 3NF。

## 决定二：明确字符串身份与状态比较

默认 `utf8mb4_0900_ai_ci` 用于一般文字及用户名。用户名唯一性因此忽略大小写和重音差异；P2 的注册规范化、冲突提示和登录比较必须一致。没有新增用户名登录规则或实现认证。

请求键、业务号和外部编号使用 `utf8mb4_0900_bin`，不折叠大小写；该排序规则的 NO PAD 属性使尾空格参与比较。相比默认 ai_ci 或旧 `utf8mb4_bin`，它避免不同请求标识被大小写或填充比较合并。[MySQL 官方比较规则](https://dev.mysql.com/doc/refman/8.4/en/charset-binary-collations.html)

状态、角色和受约束代码采用区分大小写的比较及 CHECK，拒绝未定义值。格式校验和规范化只在后续输入边界实施；数据库不承担将任意输入猜测转换成合法业务值的职责。

## 决定三：只把本行可证明的规则写入 CHECK

CHECK 覆盖状态集合、金额/容量范围、起止时间、本行状态与事件字段关系、模拟渠道身份。必填字段同时声明 NOT NULL；不依靠可能计算成 UNKNOWN 的 CHECK 表达式代替非空约束。[MySQL 官方 CHECK 说明](https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html)

不在 CHECK 中查询其他表或使用当前时间自动变更业务状态。付款截止用本行 CHECK 保证晚于 created_at 且不超过 created_at + 15 分钟，但不能由它证明不晚于关联时段开始。下列规则交给后续受控事务：患者/医生角色匹配；每次成功注册必有档案；每次预约必有订单；区间重叠与排班边界；实际截止 `min(created_at + 15 分钟, slot.starts_at)`；金额跨表相等；容量计数等于有效占用记录数；合法状态转换、权限与服务端模拟事件。

因此 UQ(user_id)、UQ(appointment_id) 表达“最多一个”，不是“至少一个”。UQ(patient_id, request_key) 保护请求身份；不添加 UQ(patient_id, slot_id)，保留取消后使用新请求键重新预约的合法路径。同键输入相等与重试返回已有结果仍须业务校验。

预约取消后允许保留历史 `confirmed_at`，退款后保留 `paid_at`；不能为了让状态字段看似整齐而抹去已发生事实。退款未知时允许 PENDING 并保存简短说明，明确失败后重试同一业务退款。状态的字段一致性不自动执行占号、释放或退款。

## 决定四：模拟渠道在数据库中明确限制

`payment_orders.channel` 在当前实现中非空且仅为 `MOCK_WECHAT`。数据库原始字典曾把 channel 标为可空，但同文档 V1.1 补充、PRD BR-09 与模拟设计明确要求本期订单标识模拟渠道；此收紧落实已确定范围，不引入新的支付业务。

`external_txn_id`、`external_paid_at`、`external_refund_id` 仍保留可空字段，当前 CHECK 要求 NULL，防止模拟数据被误读为真实渠道事实。未来接入真实支付需要新的设计、迁移与验证，不通过取消当前检查冒充已接入。

## 决定五：技术会话、审计与索引各有职责

P1 保留 `sessions.user_id` 为可空索引字段，无业务 FK。会话是可过期清理的框架数据，不是必须保留的预约历史；P2 认证阶段再审查关联及会话失效规则。该决定不免除未来权限和账号状态校验。

审计操作者通过 users FK 关联。USER 操作必须指定用户；SYSTEM 的 operator_id 可空，也可关联发起用户，不将规格“可为空”收紧为“必须为空”。有值时仍由 FK 保护引用完整性。多态 `target_type/target_id` 无法对所有目标表建立一个普通 FK，由未来受控写入保证目标与详情。数据库 JSON 类型仅证明格式，不能证明敏感信息未被写入。

按规格为查询职责建立必要索引，复用唯一键或外键已有的左前缀，避免无依据重复索引。索引存在不等于性能已经优化，后续用实际数据和执行计划验证；本阶段不公布未经测量的收益。

## 种子、验证与后果

种子仅在 local/demo/testing 且核心表为空时写入，避免覆盖历史。数据为明确合成的科室、医生、患者与排班；随机密码只存哈希，不公开登录凭据。初始排班按医院次日时间生成后转为 UTC。种子不伪造预约或付款成功。

数据库测试应验证实际元数据、外键、唯一键、CHECK、可空关系、精确金额与 Unicode、回滚及安全种子边界，并沿用 P0 检查。通过这些检查只证明 P1 数据模型能力；20 患者竞争最后名额、同患者跨医生冲突及支付生命周期竞争仍在 P3/P4 验收。

完整字段、索引和 ER 说明见 [P1 数据库结构](p1-database-schema.md)。这些决定没有改变冻结的停诊、取消、完成或模拟支付语义；后续实现仍遵循统一锁顺序和同事务写入业务/审计。
