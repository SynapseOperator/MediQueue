# ADR-0005：模拟支付与预约生命周期

- 日期：2026-11-17；基线 main `c7c618403df6c5ac39c8ae722ffb3e722f5c4845`。
- 依据：冻结 PRD 的付款截止、取消/过期、停诊、人工完成、容量与审计规则；数据库 V1.1 TX-02–06；模拟支付 V1.1。
- 沿用十张核心表、UTC DATETIME(3)、READ COMMITTED、DECIMAL 字符串金额，不增加迁移、队列、外部支付服务。

## 写入口与锁

`AppointmentLifecycleService` 处理 pay、cancel、expire/reclaim、refund、complete。所有状态转换先保护同一患者，再按统一资源顺序获取锁：

```mermaid
flowchart LR
    P[患者 X 锁] --> D[科室 S 锁]
    D --> O[医生 S 锁]
    O --> S[排班 S 锁]
    S --> T[号源 X 锁]
    T --> A[预约 X 锁]
    A --> B[支付订单 X 锁]
    B --> R[原退款 X 锁]
    R --> N[UTC 毫秒权威时间]
    N --> C[状态转换 + 名额 + 审计同事务]
```

候选关联查询不加锁，取得全部资源锁后验证父子身份；P2 已禁止有关联历史的时段及父级身份迁移。患者锁之后保护患者/操作员账号，医生锁之后保护医生账号；账号共享读防止停用状态在操作中变化。后台系统回收无需患者账号仍启用，否则停用账号会泄漏名额。

P2 管理员从科室向医生、排班、号源加锁，不反向等待患者。共享父锁保护付款资源资格，与管理员停诊/停用互斥：付款先提交后停诊可保留付款事实；停诊先提交则付款拒绝。已有付款的重复通知先按 paid_at 识别，再考虑截止/停诊，因此不会把旧付款误判为首次晚到事件。真实双向锁顺序测试见验证记录。

`DB::transaction(..., 3)` 对死锁/锁超时最多三次完整重试。连接丢失时丢弃旧连接并提示提交结果尚未确认，不自动发出新的业务操作。用户刷新原预约、订单、退款后重试原操作，已提交的终态幂等返回；未提交的操作重新经过完整锁和资格检查。与创建时的 request_key 不同，生命周期已经有稳定的预约/订单/退款 ID，不额外增加幂等表。测试在真实 COMMIT 后受控抛连接异常验证该路径，不冒充实际网络断线。

## 状态与容量

| 操作 | 预约 / 订单 / 退款 | 容量及边界 |
|---|---|---|
| 模拟付款 | PENDING_PAYMENT→CONFIRMED / UNPAID→PAID | 不再次占号；必须严格早于 expires_at，且资源开放；保留首次付款时间 |
| 未付款取消 | PENDING_PAYMENT→CANCELLED / UNPAID→CLOSED | 释放一次；患者必须早于开始，若已到截止则执行过期 |
| 到期回收 | PENDING_PAYMENT→EXPIRED / UNPAID→CLOSED | 锁内 now >= expires_at 才释放一次；不能复活 |
| 已付款取消 | CONFIRMED→CANCELLED / PAID→REFUND_PENDING / 创建 PENDING | 原子释放一次并保存唯一全额退款义务 |
| 模拟退款 | CANCELLED 不变 / 成功后 REFUNDED / PENDING、FAILED、SUCCEEDED | 沿用原退款 ID/编号/金额；失败或未知不恢复预约、不占号 |
| 登记完成 | CONFIRMED→COMPLETED / PAID 不变 | 管理员核实且已到就诊开始，完成保留占用，不能取消 |

患者只操作本人记录；管理员异常取消需勾选核实未就诊并填原因，停诊原因要求排班已 SUSPENDED；就诊开始后只能管理员按实际情况逐条处理未完成预约。没有后台按时间自动完成或停诊批量取消。

状态变更、条件 `occupied_count > 0` 减一、订单、退款及审计在同一事务；任一步失败全部回滚。paid_at 保留付款事实，released_at 只随实际取消/过期写入；重复终态先返回，不二次减量、插退款或成功审计。COMPLETED 仍属于计数口径。

## 定时与按需回收

每分钟运行 `mediqueue:expire-appointments --limit=100`，命令接受1–1000的批量上限；调度器用 withoutOverlapping 防任务重入。最终正确性依靠行锁及状态幂等，不依赖调度器缓存锁。

创建预约前在业务锁之外扫描“本患者 OR 目标号源”的到期候选，最多100条，按 expires_at/id 排序；每条调用同一 expire 独立短事务。完成后才进入原 P3 创建事务。不能持有目标号源锁再去获取其他患者锁，避免与创建/取消形成等待环。回收事务已提交后，即使后续新预约失败，也不撤销已合法回收的历史。

仅到达截止不改变占用；候选最终锁内再次判断，付款、取消或另一回收已先处理时安全跳过。批量有界意味着超过100条积压或等待中刚到期的记录可留给下一分钟/原请求重试，不跳过未回收占用假装有余量。调度器需要部署进程持续运行；README 提供本地 schedule:work 与 cron 方式。

## 模拟网关和权限

`PaymentGateway` 定义 payment/query/close/refund，唯一实现 `MockWeChatGateway`。结果只来自明确场景选择的服务端模块，金额、币种、订单编号、渠道和退款编号与锁内原记录核对，禁止客户端覆盖。模拟没有外部资金账本；query 读取当前持久化订单事实，close 返回本地可提交关单状态，不伪造微信响应或验签。

支付与退款的开关默认 false，限定 local/demo/testing；production 即使开关为 true 仍拒绝。付款是本人 Session、PATIENT、CSRF 加五分钟签名链接；退款要求 ADMIN 和 CSRF。不使用公开可登录密码或对外无保护事件端点。全部 external_* 资金字段保持 NULL。

取消已付款预约先可靠保存退款义务，管理员在预约详情显式处理模拟退款结果。这符合冻结规范“模拟退款处理后确认结果”，避免取消事务把失败/未知描述成退款成功。失败/未知沿用原退款行重试，成功终态优先，不会被后来的失败覆盖。界面显示真实持久化状态、失败/未知说明以及“无实际扣款/资金流转”。真实渠道、异步通知/对账、二维码和外部退款不是本次实现。

## 验证与阶段边界

真实 MySQL 验证涵盖九种双进程生命周期竞争、全部历史抢号测试、支付/取消/过期/退款/完成审计写失败、退款插入失败、未知提交响应、时间边界及 HTTP 安全约束。详见 [P4 验证记录](../archive/verification/P4.md)。

P5 页面体验、统计、复杂 SQL/存储过程与函数，P6 性能/EXPLAIN、备份恢复和综合验收留待后续阶段。没有为模拟支付引入未经验证的真实渠道适配器。
