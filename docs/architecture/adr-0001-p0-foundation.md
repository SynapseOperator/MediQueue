# ADR-0001：P0 工程基础与交付边界

- 日期：2026-11-16
- 状态：P0 实施决定；阶段验收以 PR 和实际 CI 结果为准
- 依据：[总指令](../../CODEX_START_PROMPT.md)、[PRD V1.1](../spec/MediQueue_PRD_V1.1.md)、[数据库设计 V1.1](../spec/MediQueue_Database_Design_V1.1.md)、[模拟支付设计 V1.1](../spec/MediQueue_Mock_WeChat_Payment_Design_V1.1.md)

## 背景与授权

用户已明确授权进入工程开发，并要求本轮仅完成 P0，验收后再进入 P1。设计文件中“尚未编码”“不是编码授权”等文字记录其编写时的状态；当前明确授权覆盖旧的阶段限制，不改变冻结业务规则。规格优先级为 PRD、数据库设计、模拟支付设计。

## 决定

使用 PHP 8.4、Laravel 13、MySQL 8.4，以及 Blade、Tailwind CSS、Vite 构建单体应用。Windows 本地可使用便携 PHP，MySQL 优先通过 Docker 运行。CI 使用真实 MySQL service，依赖按锁文件安装。所用精确版本、命令和结果由交付记录提供，不将本决定视为已经通过验证的证明。

Laravel 13 的 PHP 支持与维护周期依据 [官方版本说明](https://laravel.com/framework/docs/13.x/releases) 核对；本项目选择 PHP 8.4，并提交 Composer/npm 锁文件固定实际依赖版本。

P0 只提供最小工程、演示配置边界和 MySQL migration/健康验证基础设施。十张核心业务表在 P1 按正式数据字典创建；移除 Laravel 默认 users/auth 迁移，避免其默认邮箱登录模型与冻结的 username/password_hash/role 模型冲突。

Session 使用数据库存储，P0 迁移创建实际使用的 Laravel `sessions` 技术表，框架另维护 `migrations` 记录表。两张技术表不计入十张核心业务表。`sessions.user_id` 暂为可空索引字段，不声明指向尚未创建的 `users` 表的外键；P1 在建立业务账号时审查会话关联。数据库测试使用独立 fixture 表证明外键、CHECK 与回滚行为，不将测试表纳入业务 schema。

Cache 使用文件存储，queue 使用同步驱动。当前无需 Redis、后台队列服务或前后端双工程；这些设施不能仅为预留未来用途而引入。

应用存储与时间比较使用 UTC，医院展示使用 Asia/Shanghai，业务日期按医院时区解释。数据库使用 InnoDB、utf8mb4。迁移账号负责结构管理；独立运行账号只具有所需业务读写权限。凭据不入库，示例配置不含真实秘密。

唯一支付渠道为 `MOCK_WECHAT`。界面明确标注“模拟微信支付／无实际扣款”；生产模式不开放模拟付款入口。P0 不提前实现真实支付适配器、付款 API 或完整模拟付款服务。

新仓库先将规格及最小开源文件推送 `main` 作为基线，再通过 `feat/p0-foundation` PR 提交工程。`main` 要求 PR 和必需 CI；阶段 PR 在实际 CI 通过后才 Ready for Review。所有 PR 等待负责人审核，不自动合并。

## 影响与替代方案

上述选择保留单应用、单 MySQL 的开发与演示路径。相比引入独立前端、Redis 或消息队列，当前方案减少环境依赖，并符合规格范围。真实 MySQL 测试比 SQLite 配置成本高，但能验证目标数据库的外键、事务和约束行为；SQLite 不能替代关键验收。

默认框架认证表不适合作为冻结业务模型，因而不将其作为 P0 业务成果。P1 将建立规范要求的十张核心表。数据库会话提供有实际用途的 migration DDL，无需为 smoke test 增设一次性应用表；技术表和测试 fixture 均不计入业务表或业务验收。

## 后续必须保持的规则

- 一个患者账号一份档案；一个成功预约恰有一个业务订单，同事务建立。
- 区间使用半开区间；付款截止为创建后 15 分钟与就诊开始中的较早者，到达截止立即失效。
- 占用包含未回收待支付、已确认和已完成；取消/过期仅释放一次，支付和完成不改变占用。
- 生命周期按统一顺序锁定患者及资源；患者跨医生冲突检查与占号在受保护的事务内完成。
- 请求键重试核对输入；金额为历史快照；有历史引用的记录不破坏关联或物理删除。
- 停诊只阻止新预约和待支付付款，既有预约由管理员逐项处理；完成由管理员核实登记。
- 模拟退款失败仍保留退款义务，不恢复预约、不重复释放；外部真实渠道编号保持 NULL。

7 天预约窗口、30 分钟默认时段、60 秒回收频率属于建议参数，不将其改写为冻结规则。数据库设计中只列 AC-01—AC-26 的旧索引不缩减 PRD 验收范围：后续还须覆盖 AC-27—AC-30；真实支付 AC-22 是未来条件项，不阻断本期模拟交付。模拟订单必须明确记录 `MOCK_WECHAT`，不以可空的 channel 字段省略渠道身份。

## 验证与后续阶段

P0 验证包括 Composer 校验、PHP 风格/语法、前端构建、依赖与敏感信息检查、真实 MySQL 连接/migration/健康测试，以及对应 GitHub Actions。具体通过状态仅以实际运行记录为准。

P1 建立业务表、约束、基础 seeders 与数据库测试；P2 实现账户与资源权限；P3 实现预约和独立连接并发测试；P4 实现模拟支付与生命周期；P5 实现业务页面与统计；P6 完成全量验收、性能证据与备份恢复。P0 完成不代表这些业务验收已经通过。
