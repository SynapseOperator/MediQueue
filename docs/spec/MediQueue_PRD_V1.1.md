# MediQueue 产品需求规格说明书（PRD）

**版本：V1.1｜日期：2026-11-16**  
**状态：前四轮业务基线冻结；支付路线已确定为模拟微信支付；实现和测试尚未开始。**  
**课题：实践项目6——医院看病预约应用。**  
**适用范围：个人独立完成，计划周期2–3周，数据库课程设计。**

> 本文不是软件已实现的说明，也不是编码授权。当前只进行需求与设计。根据用户补充，老师仅要求JSP或PHP，未说明禁止框架；本项目决定采用PHP并**优先选择Laravel**（最终仍须核对运行环境）。由于没有微信支付商户资质，**本期只实现明确标注的模拟微信支付，不发生真实交易**；通过支付服务接口保留未来接入微信支付API v3的扩展点。任务书写的是“在线挂号支付”，老师是否接受模拟付款作为课程验收，尚未获得正式确认。本文与《MediQueue 数据库逻辑设计 V1.1》《MediQueue 模拟支付设计 V1.1》配套使用.

## 2. 项目目标与范围

项目交付目标是一个真实连接MySQL、可稳定演示预约全流程、能够用测试证明关键数据一致性的课程系统。重点是预约名额、患者时间冲突、支付与取消的状态协调，而不是构建完整医院信息系统。

### 2.1 本期必须交付

患者注册登录与基本资料；科室和医生介绍；按医生、日期查看排班及号源；创建待支付预约；支付及预约确认；患者取消；管理员停诊与逐项处理；管理员登记完成；定时及按需过期回收；患者历史记录；医生只读工作台；后台基础统计；关键操作审计。

医生工作台、统计和审计可在患者主流程之后实施，但仍属于本版目标，不能因其后开发而默认为可删除。

### 2.2 明确不纳入本期

多医院/多院区、家属代挂号、在线诊断和问诊、病历与处方、医保结算、候补排队、候诊叫号、预约改期、短信/邮件通知、复杂循环排班、微服务架构。取消后重新预约是两次独立操作，不保证原号源或新号源一定可得。

所有演示资料使用合成数据。本系统不用于真实临床服务，不采集真实患者病历。

## 5. 关键业务规则

### BR-01 时间区间与预约资格

预约区间采用半开区间[start_at, end_at)。09:00–09:30与09:30–10:00不冲突；09:00–09:30与09:15–09:45冲突。

只有尚未开始、已发布且未停诊的号源可以新建预约。资格判断使用取得必要锁之后的权威当前时间，而不是页面打开时的时间。默认可预约窗口见D-01。

患者时间冲突检查包括未到期的待支付预约、已确认预约；已完成记录的原始时段仍保留，不能通过提前登记完成绕过原时段冲突。已取消和已过期不阻止重新预约。不能只检查同一个slot_id。

### BR-02 待支付占号与截止

创建成功立即占用一个名额，并且同时生成一个业务支付订单。支付最长15分钟；实际截止不晚于就诊开始。页面必须显示实际剩余时间，接近就诊时间时不能仍承诺完整15分钟。

当前时间达到或超过截止时，支付资格即失效。清理任务是否运行不影响这项资格判断。定时任务是回收存储状态的机制，不是延长付款资格的机制。

### BR-03 号源容量

已占用数表示尚未释放或已经实际消费的名额，包括尚未回收的待支付记录、已确认与已完成记录。它不是简单的“当前未结束患者数”。

取消与过期各释放一次；支付确认不再次占号；完成就诊不回补名额。关闭或停诊时，即使数值上有剩余，也不对外销售。

管理员减少容量时不得低于已占用数。建议时段开始后冻结容量，避免历史利用率随意改变。

### BR-04 取消与重新预约

患者只能在时段开始前取消已确认预约；开始时刻不允许再自行取消。仍在待支付状态但实际已经过期的记录优先按过期处理。

取消与名额释放在同一事务提交。已支付的取消同时形成退款义务，但页面不能宣称资金已到账。重复取消返回既有结果，不重复减计数或创建退款。

取消后可以重新预约，条件仍为未开始、未冲突且有剩余容量；必须生成新的预约记录和新的提交请求标识，不能复活旧记录。

### BR-05 停诊与恢复

停诊只阻止新增预约和待支付付款，不自动取消全部既有预约。既有待支付记录继续按原截止到期；已确认记录等待管理员逐项处理。

支付或预约与停诊并发时，必须按事务中受保护的先后顺序形成一致结果，不能允许“停诊已生效但旧校验仍继续付款”的路径。

恢复出诊后，仍未过期的待支付记录可按规则继续支付；已过期、已取消记录不恢复。恢复不重置15分钟截止。

管理员处理停诊等医院责任问题时，可以对尚未实际就诊的记录逐项取消，即使时段已经开始；必须填写原因并留痕。这是管理员异常处理权限，不放宽患者自助取消规则。已完成记录不直接回退为取消。

### BR-06 完成就诊

只允许管理员在核实实际就诊后，将已确认记录标记为已完成。建议至少不得早于时段开始，并记录completed_at和completed_by。

时间过去不等于完成，也不等于爽约。尚未核实的历史已确认记录显示“就诊结果待核实”，不自动新增“爽约”处罚规则。完成操作不释放容量，不能逆向修改付款事实。

### BR-07 排班修改与历史保护

已有预约引用的排班、号源不得改医生、归属关系或起止时间，否则会改变已承诺的预约时间。需要调整时先暂停并逐项处理，另建正确时段，不提供一键迁移。

价格变更只影响新预约；旧预约和已生成订单使用预约时的金额快照。医院基础资料以停用代替直接删除；有历史引用的业务记录不得级联删除。

### BR-08 重复请求与状态回退

预约提交使用请求标识。同一患者、同一请求标识、同一业务输入的重试应返回原预约；同一标识对应不同输入应拒绝。

支付回调、取消、过期回收、完成登记、退款确认都必须可安全重试。终态不得因旧页面或旧请求被覆盖。不存在“所有重复请求都返回成功”的通用规则；应返回真实现有结果。

### BR-09 支付事实与预约资格分离

本版正式选用模拟微信支付（`MOCK_WECHAT`），绝不创建真实微信订单，也不使用真实资金。页面与报告明确告知为“演示付款/模拟退款”。模拟付款通过服务端控制的测试流程触发，所有订单更新仍要执行同样的资格判断、事务、幂等和审计逻辑；浏览器不能通过传入`status=PAID`直接更改支付事实。

支付应用层区分“可替换的网关接口”“模拟支付实现”“预约/订单核心服务”。本期必须让模拟服务跑通创建订单、付款确认、查询、重复通知/重试、退款成功或失败演示；可以预留真实微信Native适配器的方法形状，但**没有商户号和密钥时不能验证真实下单、真实通知验签及真实退款**，不得将接口占位实现说成已接通微信。

未来如取得商户资质，再单独接入真实微信支付API v3。届时必须处理请求认证、平台签名验证、真实异步通知、主动查单、关单、退款及异常补偿；任何真实渠道验签不能使用模拟签名逻辑替代。该升级不属于本次课程交付范围。

### BR-10 过期回收机制

定时任务扫描到期候选，并按小批次、短事务处理。预约请求同时针对目标号源及当前患者相关过期占用进行按需回收，再重新判断可预约条件。

两条入口复用同一套回收规则。候选扫描不代表最终确认到期；实际写入前须重新检查状态与时间。请求中不得先锁号源，再临时逐个锁其他患者造成与正常预约相反的加锁顺序。

任务失败后允许重跑；不能重复释放容量。回收与预约并发竞争后，页面仍可能提示刚刚售罄，这是正常竞争结果，不是数据错误。

### BR-11 身份与数据最小化

姓名与联系方式用于预约展示和必要联系；不强制身份证，不建立真实身份核验流程，也不声称姓名和电话能证明实名。演示只用虚构资料。

手机号按字符串存储，第一版不将其当作患者身份唯一键。登录账号与患者档案的一对一关系，是“同一患者”业务校验的范围，不声称能识别同一自然人的多个不同账号。

## 7. 统计口径

| 指标 | 定义与注意事项 |
|---|---|
| 新建预约数 | 按预约created_at统计，包含后来取消/过期的记录 |
| 当前已确认数 | 当前状态为CONFIRMED；不包含已完成 |
| 已完成就诊数 | 管理员核实后的COMPLETED记录；不能按时段已结束推算 |
| 当前名额占用率 | 在一致性已核验的前提下，指定时段occupied_count总和/容量总和；包括待支付占用及历史已完成消耗 |
| 已支付有效预约量 | 指定时段中CONFIRMED与COMPLETED数量，不能与“当前待支付占用”混用 |
| 取消率 | 采用同一创建日期队列的已取消数/该队列新建预约数；页面标明统计口径 |
| 模拟支付、模拟退款和模拟净额 | 仅基于本地模拟确认与模拟退款统计；页面、截图和报告必须标注为模拟金额，不等于实际收款或会计收入 |
| 待处理事项 | 停诊未处理预约、就诊结果待核实记录、退款待处理或失败记录 |

按就诊日期的容量统计与按订单创建日期的数量趋势应分开呈现。多表聚合前应明确数据粒度，避免容量被同一时段下的多条预约重复累加。

## 8. 非功能要求与数据库专项成果

### 8.1 正确性、安全与可维护性

后端实施身份和归属校验；密码只存哈希；数据库操作采用参数化方式；会话、表单提交和展示内容按最终技术栈配置基本保护。应用运行账号不承担数据库结构管理权限。密码、支付凭据、完整请求体和不必要的个人资料不写入审计日志。

以上是本项目的设计要求，不代表系统已通过安全测评。只需一个Web应用和一个MySQL实例；暂不引入Redis、消息队列或微服务。

关键失败应有可读提示和可定位的操作标识。预约、支付、取消、回收、完成与管理员重要修改需要保留审计；查询浏览不必逐条记录。

### 8.2 课程专项成果

提交ER模型、关系模式、数据字典、主外键与检查约束说明、事务边界、并发测试、异常回滚验证、复杂统计查询、视图、一个有实际意义的统计存储过程和一个时间区间判断函数设计，以及索引优化的真实执行计划和测量结果。

报告解释合理冗余：名额计数是可核验缓存，预约金额是历史快照；不能把所有关联字段复制到预约表，也不能声称所有跨表规则都由CHECK保证。

## 9. 验收矩阵

所有条目为待执行验收条件，不是已经通过的测试。AC-22是未来接入真实渠道时的条件项，**不是本次模拟支付交付阻断项**。模拟支付专属验收新增AC-27至AC-30。

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AC-01 | 创建患者账号并登录 | 一个账号仅有一份患者档案；可访问本人记录 |
| AC-02 | 正常预约与支付 | 预约、订单各一条；占号一次；支付确认不再增加占用 |
| AC-03 | 20个独立患者并发争抢剩余1个名额 | 恰好1个成功，其余合理失败；不存在超卖或孤立订单 |
| AC-04 | 同一患者并发预约不同医生的重叠时段 | 最多1个成功；相邻不重叠时段可以成功 |
| AC-05 | 请求返回丢失后使用同一标识重试 | 返回同一预约，不重复占号、不创建第二个订单 |
| AC-06 | 取消后用新标识再次预约同一时段 | 条件满足时成功；旧记录保留 |
| AC-07 | 在预约写入中途制造异常 | 占号、预约、订单及相应审计全部回滚 |
| AC-08 | 超过付款截止但定时任务尚未执行 | 支付立即被拒绝；不会因状态暂未清理而允许付款 |
| AC-09 | 定时与按需回收同时处理同一预约 | 只释放一次，计数与记录一致 |
| AC-10 | 支付与过期处理竞争 | 得到一个合法状态组合，不出现已释放却仍确认的预约 |
| AC-11 | 同时支付与取消 | 最终组合一致；若存在已扣款事实则产生必要退款，不丢失资金事实 |
| AC-12 | 取消已支付预约，退款失败 | 预约取消、名额已释放；退款失败可见，不显示已到账 |
| AC-13 | 时段开始前、等于开始、开始后取消 | 患者只在严格早于开始时可取消 |
| AC-14 | 停诊与新预约/支付并发 | 停诊生效后的操作被阻止；既有记录不被批量删除 |
| AC-15 | 停诊后待支付预约 | 不能付款，原截止不重置，到期可回收 |
| AC-16 | 管理员登记完成 | 只接受合法已确认记录；操作者与时间可查；名额不回补 |
| AC-17 | 时段已经结束但未人工登记 | 保留待核实状态，不自动完成、不自动标记爽约 |
| AC-18 | 修改容量或已有预约时段 | 不能低于占用，不能修改已承诺时段；失败不留局部更新 |
| AC-19 | 患者读取别人记录、医生修改排班 | 后端拒绝，不能只靠隐藏按钮 |
| AC-20 | 修改号源挂号费 | 新预约使用新价，历史预约与订单金额不改变 |
| AC-21 | 多次退款确认或重试 | 同一业务退款不重复入账；结果可核验 |
| AC-22 | 真实支付的迟到成功通知（条件项） | 记录资金事实；不复活已取消/过期预约；进入退款/异常处理 |
| AC-23 | 删除已被引用的医生、排班等 | 拒绝破坏历史关联；支持停用或关闭 |
| AC-24 | 聚合统计和容量核对 | 与人工核验的小样本一致，无连接放大 |
| AC-25 | 大规模合成数据查询 | 提供实际环境、数据规模、索引和执行计划；不伪造加速比例 |
| AC-26 | 数据备份恢复后演示 | 账号、排班、预约与订单关系可恢复，完整流程可运行 |
| AC-27 | 模拟微信支付完整流程 | 模拟页面有醒目标识；成功后由服务端更新订单及预约，无真实资金交易 |
| AC-28 | 模拟支付的重复通知、恶意直接改状态与超时竞争 | 重复事件仅生效一次；浏览器无法任意指定PAID；过期/停诊拒绝付款 |
| AC-29 | 模拟退款成功、失败、重试 | 退款结果独立展示，失败不恢复预约、不重复释放号源或退款 |
| AC-30 | 无微信商户配置时运行 | 系统使用MOCK_WECHAT正常演示；不会尝试真实下单；真实网关保持禁用 |

并发测试应使用多个独立连接和同步起跑，而不是只打开两个页面就认定完成并发验证。涉及15分钟的自动化测试可使用受控测试时钟/测试数据，生产规则保持15分钟，演示说明不得隐瞒测试条件。
