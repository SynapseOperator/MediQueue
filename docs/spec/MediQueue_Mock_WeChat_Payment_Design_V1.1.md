# MediQueue 模拟微信支付设计（技术方案）

**版本：V1.1｜日期：2026-11-16**  
**状态：设计稿；未编码、未接入真实微信支付、未运行任何交易。**  
**依据：**《MediQueue PRD V1.1》《MediQueue 数据库逻辑设计 V1.1》及用户最新决定。

## 1. 核心范围

- 本期采用 `MOCK_WECHAT`，用于课程演示。所有付款、退款金额均是**本地数据库的模拟金额**，不是微信、银行卡或银行账户中的资金。
- 不需要、不申请、不配置微信商户号、APPID、API v3密钥、商户私钥及平台公钥，也不生成真实微信支付 `code_url`。
- 保留可替换的支付网关边界，但**不要求**本次编写未经商户环境验证的完整微信支付SDK适配器；这样不会把时间消耗在无法验证的真实接入细节上。
- 首页、支付页、订单详情和课程报告清晰标注“模拟微信支付／演示环境”。二维码如需展示，只编码项目自己的模拟收银台链接，并明确标注“演示二维码”，不得复制真实微信支付收银台的官方身份标识或收款承诺。

## 2. 建议的分层

| 层次 | 职责 | 本次交付 |
|---|---|---|
| 预约业务服务 | 创建预约、资格检查、锁、占号、取消与过期 | 必须真实实现、连接MySQL |
| 支付应用服务 | 驱动订单、支付确认、模拟退款、状态与幂等 | 必须真实实现、连接MySQL |
| 支付网关接口 | 抽象“发起支付、查询、退款、关闭”等能力，不泄漏支付渠道细节 | 必须定义并由模拟网关实现 |
| 模拟微信支付网关 | 生成模拟收银台/链接、发出演示成功或失败、模拟退款与重试 | 本次唯一启用的网关 |
| 微信支付Native API v3网关 | 未来接入真正的 `code_url`、认证签名、验签通知与退款 | **本期不启用、不对外声称已验证** |

> 支付网关接口旨在将来容易替换，不引入微服务、消息队列或额外复杂中间件。实现时允许采用一个简单的PHP接口和两个小型服务模块。

## 3. 演示端到端流程

1. 患者登录、选科室/医生/时段，预约服务在MySQL事务内占号、创建`appointments`及`payment_orders`，订单状态为`UNPAID`。
2. 系统展示订单金额与实际截止时间：`min(创建时间+15分钟, 就诊开始时间)`。页面显著提示“模拟微信支付，测试用途，无实际扣款”。
3. 可点击“模拟支付成功”（首选，可在单机稳定演示）；若有足够时间，可生成指向项目自身模拟收银台的**演示二维码**。二维码不是真实微信Native支付码。
4. 受控服务端演示模块产生模拟支付事件。支付应用服务在事务内验证订单归属、未过期、排班未停诊、金额、状态等，并做幂等更新：`UNPAID→PAID`，`PENDING_PAYMENT→CONFIRMED`。仅更新数据库一次，不重复占号。
5. 页面重新查询服务器端订单状态后展示“模拟付款成功”；不得仅依赖前端按钮响应认定完成。
6. 患者在就诊开始前取消：预约变为`CANCELLED`，占号释放一次；模拟退款记录被创建。模拟退款处理后将状态变为`SUCCEEDED`或`FAILED`，记录审计并在前端准确展示。
7. 到期未支付：定时任务和预约时按需回收将预约设为`EXPIRED`、订单设为`CLOSED`、释放一次号源。模拟支付不允许在截止后使其恢复。

## 4. 最小但充分的技术规则

- **清楚标识：** `payment_orders.channel=MOCK_WECHAT`；所有演示金额和状态均标为模拟，`external_txn_id`、`external_paid_at`、`external_refund_id`保持NULL。
- **不信任客户端：** 正常应用入口不能接受来自浏览器的 `paid=true` 或 `status=PAID`。模拟成功是启用的演示支付网关经过服务端订单校验后产生的事件，且仅在明确的本地/演示模式开放。生产模式关闭模拟付款入口。
- **支付与退款分离：** 本地模拟付款成功不代表真实资金流动，模拟退款成功也不代表银行卡或微信零钱收到退款。
- **事务保持：** 对付款、取消、超时、停诊和退款同样使用第四轮规定的短事务和锁顺序；模拟模式不允许绕过数据库业务规则。
- **幂等：** 对同一订单重复确认只应生效一次；退款重试沿用同一业务退款记录；取消与回收绝不重复减容量。
- **安全与可演示性：** 演示付款入口限制在明确的演示环境，使用受控订单会话/短期演示凭证；不要对互联网暴露无保护的“任意订单付款成功”端点。手机扫码测试如果没有可达地址，可用浏览器内演示按钮完成全流程，不把手机网络连通性当成业务验收条件。
- **可测故障：** 测试模式能触发付款成功、拒绝、重复确认、超时、退款成功、退款失败，但不伪造真实微信签名或声称真实渠道回调已验签。

## 5. 数据库模型与状态

维持10张核心表，不增加所谓“微信订单表”。本期演示订单使用现有`payment_orders`，退款使用`refunds`，可审计动作使用`audit_logs`。真实网关若未来涉及多次扣款或异步通知，需另外审查扩展表。

正常状态：`appointments: PENDING_PAYMENT→CONFIRMED`，`payment_orders: UNPAID→PAID`。过期：`appointments: PENDING_PAYMENT→EXPIRED`，`payment_orders: UNPAID→CLOSED`；已模拟付款后合法取消：预约`CONFIRMED→CANCELLED`，支付订单`PAID→REFUND_PENDING→REFUNDED`，退款记录`PENDING→SUCCEEDED`。退款失败时保留`refunds.status=FAILED`和待处理义务，绝不恢复预约。

## 6. 本期验收

| 测试 | 预期结果 |
|---|---|
| 正常模拟付款 | 一个预约、一个订单，状态更新一致；占号只发生一次 |
| 重复演示付款事件 | 第二次不新增支付事实、不重复占号、不改变首次时间 |
| 过期付款 | 截止时及之后拒绝确认，清理后容量释放一次 |
| 停诊后模拟付款 | 未确认预约不得支付，旧截止继续有效 |
| 同时付款和取消 | 只形成一个可解释的最终状态及必要退款 |
| 模拟退款失败再试 | 预约保持已取消，退款记录可重试，不重复退额、不重新占号 |
| 权限与环境控制 | 不能随意输入另一用户订单号完成付款；非演示环境不开放模拟成功入口 |
| 报告透明性 | 系统截图和文字都明确写明模拟，不出现“已真实接入微信支付”的错误表述 |

## 7. 未来真实接入的边界（不是本期任务）

微信支付官方Native支付流程会由商户后端向微信下单获取`code_url`，并在确认真实支付结果时通过通知和/或查单更新商户订单；接入还涉及商户身份与签名/验签、关单和退款。无商户资质时不应冒充真实微信返回的`code_url`，也无法证明真实渠道回调或退款已经通过。官方参考：

- 微信支付Native开发指引：https://pay.wechatpay.cn/doc/v3/merchant/4012791891
- 微信支付Native下单：https://pay.wechatpay.cn/doc/v3/merchant/4012791877
- 微信支付Native成功回调：https://pay.wechatpay.cn/doc/v3/merchant/4012791882

如果未来有可用商户资质，再单独设计真实事件持久化、验签、安全配置、退款和对账验收；不用本次课程项目提前实现无法验证的全链路。
