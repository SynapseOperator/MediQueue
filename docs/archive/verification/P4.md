| 取消/退款 | 未付关闭；已付取消一次释放并创建唯一全额退款；FAILED/UNKNOWN沿用原记录，成功终态不被后来失败覆盖；患者开始时不能取消，管理员须原因；COMPLETED不可取消 |

| 定时与按需 | ExpiryIntegrationTest：本患者OR目标时段候选，其他患者的其他时段不受影响；命令limit、每分钟调度与withoutOverlapping；回收审计失败不泄漏名额，不继续新预约；旧键返回已过期历史，新键才重新创建 |

## 真实多进程竞争

LifecycleConcurrencyTest 使用独立 PHP/PDO 进程、患者锁门闩与输入信号同步；停诊场景在实际科室行锁取得后暂停领跑者，确保相反两种顺序都被执行。每条证据记录独立PID、CONNECTION_ID、测试UTC时刻、最终状态、成功审计次数、退款与容量核对。只在测试进程使用受控时间，不改变生产15分钟规则。

## 浏览器、业务库与复核

真实Chrome：新建虚构患者→预约→模拟支付成功→本人取消，页面确认CONFIRMED/PAID、CANCELLED/REFUND_PENDING与“待处理（仅模拟）”，始终注明无实际扣款，最后退出。管理员退款的真实浏览器交互未执行：没有可安全共享的临时管理员登录凭据；不为此重置已有管理员密码。相应管理页面和失败重试闭环已通过真实HTTP+MySQL测试，不能把它称为浏览器已验证。

应用库原8用户/1预约/1订单，最终9用户/2预约/2订单/1退款：旧预约由真实调度过期，新虚构预约由浏览器付款后取消；当前退款PENDING等待管理员处理。单SQL检查全部号源账实差异0。未清空数据或手工修正占用。

独立代理只读复核业务锁顺序、截止、晚到/重复事件、权限、退款终态、并发同步与COMMIT注入时机，结论无阻断。复核建议的UNKNOWN中文提示与提交响应丢失直接证据已落实。

本次实际读取main保护成功：要求PR及quality/mysql/frontend/secrets，strict、enforce_admins、conversation_resolution开启；禁止强推/删除，审批数0。

## 限制与下一阶段

- 仅本地数据库模拟付款/退款，没有真实微信、资金、回调验签或外部对账。退款由管理员逐条触发，失败/未知要继续处理原退款。
- 调度需持续运行；批次有界，积压或等待中刚到期的记录留待下次调度/原请求重试，不能假减容量。
- 当前是课程级同步竞争验证，不是吞吐量基准或长期压测；演示前需确认 MySQL 与回收调度器正常运行。
