# P6 独立性能实验

2026-11-17，本机 MySQL 8.4.13，Windows，内存约 34.0 GB。实验运行于独立 `mediqueue_perf_p6`，按项目迁移建立同版结构，未修改业务库或删除业务索引。`php scripts/performance/run.php` 仅在该库不存在时创建；已有实验库默认拒绝覆盖，`--measure-existing` 仅用于本次合成数据测量并会更新该库中的合成时间戳。脚本需要本地 `.env.migration` 和 `.env.database`；管理员密码只在进程内读取，不写入参数或结果。不要将此命令指向业务数据库。

数据：50,000 虚构患者各一条预约、1,000 个不重叠时段各 50 个名额，50,000 个待支付订单；均为过期未回收的待支付，号源占用均为 50。预约创建时在可预约窗口，15 分钟截止早于时段开始；无退款。数据库检查预约 50,000、订单 50,000、占用差异 0。它是均匀、单状态的合成负载，不代表真实医院流量，也不衡量全业务吞吐。

每条 SQL 先预热一次，再测 7 次取中位数，原始时延与 `EXPLAIN ANALYZE` 存 [p6-results.json](p6-results.json)。对照通过查询级 `IGNORE INDEX`，没有删除索引；结果集 SHA-256 在两个计划间一致。

| 查询 | 正常中位数 | 忽略目标索引中位数 | 观察 |
|---|---:|---:|---|
| 到期候选按截止/ID排序取100条 | 0.2820 ms | 9.6413 ms | 正常使用状态/截止/ID覆盖范围扫描；对照扫描更多索引行并排序。此数据全部已到期，选择性并不代表线上。 |
| 单患者历史按创建时间倒序取20条 | 0.2815 ms | 0.1594 ms | 每患者仅一条，本样本不能证明历史索引对长历史有明显收益；对照仍可利用患者唯一索引。 |

计时含本机客户端往返、PHP 与 PDO 取数；热缓存单次实验并非稳定基准。未测写入开销或独立索引空间，不能据此判断整体收益；本轮未提出新增索引。`EXPLAIN ANALYZE` 是只读 SELECT，但会实际执行，生产环境应谨慎评估。该性能库保留供复查；要重新生成时，须由操作者明确处理这个固定名称的实验库，脚本不会自行删除任何库。

## 第二轮：长患者历史及占用核对

独立数据库 `mediqueue_perf_p6_v2`，由 `php scripts/performance/run-v2.php` 创建；若库已存在则拒绝覆盖。数据为 100 个合成患者各 500 条互不重叠的待支付预约、1,000 个时段各 50 条预约和订单，共 50,000 条；创建时间距就诊约一天、付款期限 15 分钟，测试时间均已过期但未回收。该均匀数据直接构造、没有逐操作审计，不模拟实际流量或退款。检查结果预约与订单各 50,000 条，号源占用差异 0。

单机 CPU（24 核 / 32 逻辑处理器），内存 34,033,319,936 字节；MySQL 8.4.13，InnoDB buffer pool 134,217,728 字节、flush_log_at_trx_commit=1、binlog 开启。此独立 PDO 测量连接使用服务器默认 REPEATABLE-READ；应用连接使用 READ COMMITTED，因此本次只比较只读查询计划，不推断事务竞争性能。每个查询预热一次，顺序测量七次取中位数；SQL 常量即测试参数，完整 SQL、七轮结果、结果哈希和 EXPLAIN ANALYZE 见 [p6-results-v2.json](p6-results-v2.json)。第三项为占用视图同等的按号源分组核对查询。

| 查询 | 正常索引中位数 | 查询中忽略目标索引 | 结果 |
|---|---:|---:|---|
| 到期候选前 100 条 | 0.3130 ms | 9.0846 ms | 两者结果哈希一致；对照需扫描和排序更多行。 |
| 患者 42 历史最近 20 条（该患者 500 条） | 0.2918 ms | 0.7091 ms | 两者结果哈希一致；本合成分布下倒序历史索引减少排序。 |
| 1,000 个号源的占用核对 | 15.9117 ms | 110.8925 ms | 两者结果哈希一致；忽略号源关联索引的对照成本更高。 |

对照仅用 `IGNORE INDEX` 影响单条查询，未删除索引或改变应用 schema；实验顺序固定、单机热缓存，不能外推并发延迟。未单独测索引空间和写入成本，不能依据这些数字推荐新增索引。第一轮原始证据保留作对照，本轮覆盖了更长患者历史。

## 真实患者历史页面查询与额外核验

复测使用 `AppointmentController::index` 实际八表关联、按 `patients.user_id=44` 筛选、按预约 id 降序取 20 行（不含分页 count 查询）；完整 SQL 与计划见 v2 JSON 的 `patient_page`。正常中位 2.4467 ms，忽略 `(patient_id, created_at, id)` 索引为 2.4713 ms，返回 20 行且哈希一致。正常计划使用 `(patient_id, request_key)` 唯一索引取得该患者 500 行，再按 id 排序；**没有使用**此前简化历史查询所比较的索引。不能把简化查询结果解释为当前页面的加速收益，也未在本实验中证明新增索引有价值。

本轮再次核验：外键检查开启；预约/患者/号源/订单关系、待支付与未支付状态配对、金额与时间约束异常 0；患者重叠区间 0；bcrypt 格式哈希异常 0；号源账实差异 0。合成账户密码为运行时随机值的哈希，明文未保存。脚本拒绝配置缓存，将子进程连接固定为 MySQL 和实验库并清除 URL/socket 覆盖；重测时先核对当前库名。两库均仅作合成实验，未验证所有可能的业务跨表语义。
